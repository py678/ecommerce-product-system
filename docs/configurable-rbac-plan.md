# 可配置角色与权限实现计划

> 使用 executing-plans 在当前会话逐项实现；用户已批准实施此前方案。

**目标：** 后台先创建角色、分配权限和数据范围，再把用户分配到角色；单用户单角色。

**架构：** 保留现有用户 legacy role 列以兼容已有注册入口、同步数据和历史审计，新增 roleId 关联作为权限唯一来源。权限目录随迁移维护，角色权限可配置，范围按商品/订单的具体操作配置 OWN/ALL；ADMIN 系统角色保持保留且不可削弱，OPERATOR 作为默认注册角色不可删除或停用。权限配置和角色分配只在 PRIMARY/STANDALONE 写入，角色及分配变更整事务复制。业务鉴权拒绝 REPLICA，避免异步撤权窗口用于业务访问。

**技术栈：** 现有 NestJS、Prisma、PostgreSQL、React、Ant Design、Vitest、Playwright。

**规格：** 本次会话已批准的动态角色方案；以本文具体兼容决策补充。

## 全局约束

- 不新增任何示例业务角色；只保留现有 ADMIN/OPERATOR 并允许自行创建。
- 不实现商品归档、分类治理等此前讨论的商业化改进。
- 管理员注册保留原内部 ID 校验，新增自定义角色不可从注册接口选择。
- 权限点固定白名单；无匹配权限与范围默认拒绝。管理权限不可通过自改角色、越级授予扩权。
- list/count 同一 where，写条件包含归属；跨资源拒绝统一404。
- 角色/权限变更、用户撤权、审计同事务；权限修改撤销该角色用户旧凭证。
- 禁止 reset；迁移 --create-only，SQL 先审查，隔离验证；业务库部署需 SQL 审查确认。
- 不提交凭据、生成代码、测试输出与备份。Docker 在验证和部署许可后更新。

## 审查重点

1. 自定义只读角色直接请求写接口必须403；没有权限不能收到私有实时事件。
2. OWN/ALL 切换须同时影响列表、总数、详情、实际更新/删除条件。
3. 角色停用/改权限须撤销旧 HTTP 与 Socket 会话；过期页面不可继续修改。
4. 停用/删除默认或管理员角色、删除有用户角色、自改角色及最后管理员降级必须拒绝。
5. 副本旧资料事件不得覆盖主库角色分配；角色依赖必须在同一目标事务内先创建再关联。
