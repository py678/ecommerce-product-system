# 后台订单规格（已确认）

## 业务范围与权限

后台运营代客录单，无商城前台、真实支付、退款/退货、自动收货或客户管理模块。用户角色继续为 OPERATOR、ADMIN。两角色均可选择全部共享商品录单；订单扣库存不授予商品编辑权限。

运营人员仅查看和操作自己创建的订单，管理员查看和操作全部订单。权限点为 order:read/create/confirm/ship/complete/cancel；JWT + 权限 Guard + Service 归属条件同时执行，列表与计数共用 where。越权与不存在统一 404。创建人来自 JWT，DTO 拒绝 creatorId、role、价格、金额和任意状态等非契约字段。

## 状态与库存（不可自行变更）

- 创建：PENDING（待确认），订单创建人由服务端确定，立即扣减库存。
- **确认由订单创建人（运营人员）或管理员手动点击触发**：PENDING → CONFIRMED。不是自动确认，不是支付回调，确认不代表付款成功，也不重复扣库存。
- 发货：创建人或管理员将 CONFIRMED → SHIPPED，物流公司、运单号必填。
- 完成：创建人或管理员手动将 SHIPPED → COMPLETED。
- 取消：仅 PENDING/CONFIRMED → CANCELLED，取消原因必填，在同一事务回补库存且仅一次。
- **已发货（SHIPPED）和已完成（COMPLETED）的订单不允许取消，库存不回补。** 首版没有退货、退款或强制取消入口，管理员也不能绕过。
- 终态不能恢复；订单无物理删除 API。商品明细、数量、成交价格、客户信息创建后固定；录错时取消并重新创建。

## 数据与接口

orders 保存唯一订单号、creatorId、客户姓名/联系方式/收货地址、备注、状态、总额、物流字段、阶段时间、幂等键及请求指纹。order_items 保存商品关联与名称/封面/单价快照、数量、小计。order_logs 保存操作人及名称快照、前后状态、动作、原因和时间。历史快照不随商品修改。被订单引用的商品禁止删除，返回 409；不级联删除订单历史。

金额全程 Decimal，接口金额字符串，前端只预览，后端按事务内商品现价计算。单订单 1–50 种不同商品，每项数量 1–9999；重复商品 ID 拒绝。单价沿用 Decimal(12,2)，小计/总额 Decimal(18,2)。订单号使用随机 UUID 衍生编码并有数据库唯一约束。

POST /api/orders：{ idempotencyKey(UUID), customerName(1–80), phone(5–32，数字/空格/+/-/括号), address(1–500), remark?(最多1000), items:[{productId(UUID),quantity}] }。同一用户/键/相同请求重试返回同一订单；不同请求复用同一键返回 409。相同键并发不得重复扣库存。

GET /api/orders：page=1、pageSize=10（上限100）、search（订单号/客户姓名，最多100）、status、createdFrom/createdTo（ISO8601），createdAt desc/id desc。返回 {list,total,page,pageSize}，列表仅基础摘要，详细客户地址在详情中。

列表日期操作：保留开始/结束日期，新增“今天”“本周”快捷按钮；按浏览器本地日历计算，今天 00:00:00.000 至 23:59:59.999，本周为周一至周日。选中日期转换成明确的 ISO 时间发送到已有接口，起止边界均包含，可仅传一侧。与搜索、状态按 AND 组合，列表和总数共用归属条件；筛选回第 1 页，URL、刷新、浏览器历史和实时刷新保留条件。非法日期或开始晚于结束时前端就地提示并阻止请求；后端已有 DTO 与区间检查继续生效。前端回归见 `frontend/e2e/order-date-filters.spec.ts`，权限条件回归见 `backend/test/orders.spec.ts`。无需数据库迁移。

GET /api/orders/:id；PATCH /api/orders/:id/confirm、/complete（空 body）；PATCH /api/orders/:id/ship（carrier/trackingNo，各1–80）；PATCH /api/orders/:id/cancel（reason，1–500）。所有接口需 JWT，成功状态变更为 200；校验400、认证401、无权限403、越权/不存在404、库存/状态/幂等冲突409、副本写入503。

## 事务、幂等与并发

订单、明细、库存、日志同一事务提交，任一商品缺货则全部回滚。商品按 UUID 排序加行锁，使用 stock >= quantity 的原子扣减。幂等键使用事务锁和唯一约束。状态操作锁定归属范围内订单，再检查合法前态；取消锁定商品并回补一次，溢出也整体回滚。无论接口重试、并发取消/发货，均不能重复扣减/回补。

商品增加 stockVersion。订单扣减、取消回补及手动修改库存递增版本；商品编辑提交 stock 时必须附带读取时的 stockVersion，版本过期返回409，防止旧表单覆盖订单扣减。原有商品归属规则保持。

## 双库单写与复制

Docker PostgreSQL 是 PRIMARY，商品和订单数据在此统一写入；本机 PostgreSQL 是 REPLICA，保存副本。users/categories 保持已有双向同步。为防整行同步覆盖库存，products 与 orders/order_items/order_logs 统一主库写入，副本直接修改商品或订单被数据库触发器拒绝；主库拒绝来自副本的这些表写入。应用也拒绝在副本建单或写商品。本机前端开发代理统一指向8088主后端；本机独立后端不成为第二个订单/库存写入入口。

内部 _commerce_config 保存部署角色，不对外暴露。隔离开发/既有迁移兼容模式 STANDALONE 只用于独立环境，生产双库部署必须明确设置 PRIMARY/REPLICA。切换前停止写入并备份两库，排空原同步队列、核对商品一致，再部署结构并指定角色，不丢弃待同步业务修改。

_sync_events 新增 transaction_id。启用主副本模式后按源事务分组，目标事务整体应用、提交后再确认源事件；同事务超过原100条限制也不得拆分。失败整组回滚，严格保持源事务顺序，避免后续取消先于创建。重放由原事件版本实现幂等，源确认失败后重放不重复扣减。同步只复制库存结果，绝不在副本重跑订单扣库存业务。

## UI 与实时

新增订单管理菜单、列表、创建页、详情页；列表筛选同步URL，支持分页、搜索、状态、时间范围。创建页选商品、数量及客户信息，金额预览；提交loading、失败保留输入、网络重试保留幂等键，同一表单内容生成同一重试键。详情展示状态、物流与操作日志，取消/发货需确认及校验。

order:changed 仅通知创建人和管理员，载荷只含事件ID、订单ID和动作，不广播客户信息。订单提交后通知受影响商品，商品库存自动刷新；订单页面复用300ms合并、参数保留及重连补拉。推送失败不影响已提交订单。
